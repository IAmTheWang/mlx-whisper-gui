# internal/jobmanager

The core of the app: job state machine, a single-worker FIFO transcription queue, the `Engine` abstraction over the two transcription backends, subprocess execution, and SSE event fan-out. Fully HTTP-agnostic — `internal/server` is the only consumer.

## Files

- `job.go` — `Job` type: state machine (`Queued → Running → {Done, Failed, Cancelled}`, enforced by `transition()`/`validTransitions`), capped in-memory log ring buffer (500 lines), pub/sub for SSE (`Subscribe`/`publish`, non-blocking sends so a slow client can't stall the subprocess reader). `Job.Engine` records which engine a job was created for.
- `engine.go` — the `Engine` interface (`Name`, `PrepareCommand`, `MainArgs`, `ProgressPattern`) and `engineFor(name)`, the small registry mapping a job's `Engine` string to its implementation. Deliberately does **not** include binary resolution — that stays on `Manager` as named injected closures (see below), so the existing fake-binary test seam keeps working.
- `engine_mlx.go` — `mlxEngine{}`: builds mlx_whisper's CLI args (including the `--condition-on-previous-text False` fix, see below), no preparation step (mlx_whisper decodes video itself), tqdm-style `(\d{1,3})%\|` progress pattern.
- `engine_whispercpp.go` — `whisperCppEngine{}`: `PrepareCommand` builds an `ffmpeg`-based video→16kHz-mono-WAV conversion (skipped if the source is already `.wav`), `MainArgs` builds `whisper-cli`'s flags (`-m -f -of -osrt -pp -nt -l`, forcing `-l auto` when `job.Language` is empty since whisper-cli's own default is `en`, not autodetect, plus `--vad -vm <path>` when `config.WhisperVadModelPath` is set — see the VAD note below), and a `progress\s*=\s*(\d{1,3})%` pattern matching whisper-cli's `\n`-terminated stderr progress line.
- `manager.go` — `Manager`: job registry + `jobs.json` persistence + the worker loop that runs whichever engine a job was created for.
- `runner.go` — `Runner`: spawns a subprocess (own process group via `Setpgid`), streams stdout/stderr line-by-line, supports graceful `Cancel()` (SIGTERM → SIGKILL after 5s) and immediate `ForceKill()` (SIGKILL, used on server shutdown). Fully engine-agnostic — reused unmodified for both engines' subprocesses (including whisper.cpp's separate `ffmpeg` preparation step).
- `linesplit.go` — `lineSplitter`, a custom `bufio.SplitFunc` that splits on **both** `\r` and `\n`, because `tqdm` redraws progress bars with a bare `\r`. A stock `bufio.Scanner` would block until the whole subprocess exits before emitting anything.

## Key design points

- **One job runs at a time, across both engines.** `Manager.queueCh` is drained by a single `workerLoop` goroutine — MLX's unified-memory GPU path gains nothing from concurrent jobs on one Mac; it would only add contention/OOM risk. Don't parallelize without revisiting this.
- **Engine selection is a small interface, not a bigger plugin system** — there are only two implementations (`mlxEngine`, `whisperCppEngine`) and that's expected to stay true. `runJob` resolves the right binary via a `switch job.Engine` against `Manager`'s three named resolver closures (`resolveMlx`/`resolveFFmpeg`/`resolveWhisperCli`), then delegates command-building and progress-parsing to `engineFor(job.Engine)`. `ffmpeg` is resolved unconditionally for both engines: mlx_whisper uses it internally (Go never sees the call), whisper.cpp's engine invokes it directly for its preparation phase.
- **whisper.cpp jobs have two subprocess phases while staying `Running`**: an `ffmpeg` preparation phase (video → WAV, skipped if the source is already `.wav`) followed by the main `whisper-cli` phase. `Job.replaceRunner()` swaps the active runner reference between phases without a state transition (`markRunning` only fires once, on `Queued→Running`) so `Cancel()` keeps working correctly no matter which phase is active. The temp WAV's `defer os.Remove(...)` is registered as soon as the path is known, before either phase runs, so a cancel or a mid-conversion error still cleans it up.
- **Progress vs. log events are split** in `Manager.dispatchEvent` using the active engine's `ProgressPattern()` — mlx_whisper's bare-`\r` tqdm redraw, or whisper-cli's `\n`-terminated `progress = NN%` stderr line (reclassified out of the ordinary log stream by matching the pattern against every event, not just ones already flagged `Kind=="progress"`). A match is throttled to ~1/sec and published as a `progress` event *without* touching the capped log buffer (otherwise a few seconds of progress-bar spam would evict real early log lines before any client even connects); the parsed percent is clamped to `0-100` so a version/format mismatch can't send a bogus value to the UI. Everything else goes to the log buffer, `output.log`, and a `log` SSE event.
- **State transitions are validated** (`validTransitions` in `job.go`) — an invalid transition returns an error instead of silently corrupting state. Terminal states (`Done`/`Failed`/`Cancelled`) never transition further.
- **The `Done` transition sets the sidecar-copy outcome atomically**: `markDone(srtPath, sidecarPath, sidecarErr)` takes all three together in one `transition()` call, rather than a separate `setSidecar()` call after the state flip. The two-step version had a real, reproducible race (a concurrent reader could observe `State() == Done` with stale/empty sidecar fields between the two calls) — keep this atomic if you touch the completion path.
- **Cancellation is two-phase**: `CancelJob` on a `Queued` job transitions it directly to `Cancelled`; on a `Running` job it only sets `cancelRequested` and calls `Runner.Cancel()` — the actual `Cancelled` transition happens later in `runJob` once `Run()` returns. Don't assume `CancelJob` returning means the job has actually stopped for a running job.
- **`runJobSafely` wraps every job in a `recover()`** — a panic in one job must never take down the worker loop and silently stop all future jobs.
- **`jobs.json` persistence**: `Manager.persist()` writes the full job list (newest-first) after every state change. `loadPersisted()` on startup marks any job still `Queued`/`Running` as `Failed` ("Interrupted by server restart") — there is no resume-in-place for interrupted jobs. A persisted job with no `Engine` (written before this field existed) falls back to `"mlx"`, both here and in `engineFor`.
- **Sidecar copy is best-effort**: after a job completes, `copySrtNextToVideo` writes a copy of the `.srt` next to the source video. A failure here (read-only volume, disk full, permissions) is recorded in `Job.srtSidecarError` but **never** flips a `Done` job to `Failed` — the transcription itself already succeeded.
- **Job IDs double as filenames, shared by both engines**: mlx_whisper is invoked with `--output-name <job.ID>`; whisper.cpp with `-of <OutputDir>/<job.ID> -osrt`. Both conventions land the primary `.srt` at `<OutputDir>/<job.ID>.srt`, so `runJob`'s completion check is engine-agnostic. Output directories live under `~/Library/Application Support/whisper-gui/jobs/<job.ID>/`, not in this repo.
- **Args are passed as `[]string`, never through a shell** (`exec.Command` in `runner.go`) — filenames with spaces/special characters are handled safely with no manual escaping and no shell-injection risk. Don't introduce `sh -c` here.
- **`condition_on_previous_text` is explicitly set to `False`** in `mlxEngine.MainArgs`. mlx_whisper defaults this to `True` (feed each window's transcript back in as the next window's prompt), which helps cross-window consistency but means a single bad window — most commonly a silent/no-speech stretch that gets mistranscribed into a plausible-sounding phrase — gets fed back into the model and can lock it into repeating that exact line verbatim for the rest of the file. A repo-wide scan found this had silently corrupted a large fraction of every job's output since the app's very first use, long before it was noticed. See `notes/mlx-whisper-repetition-loop-bugfix.md` for the investigation and before/after data. Don't remove this flag without re-reading that writeup.
- **whisper.cpp's silence-repetition fix is VAD, not a context flag.** Unlike mlx_whisper, whisper-cli's underlying library already defaults `no_context` to `true` (confirmed in `ggml-org/whisper.cpp`'s `whisper_full_default_params()`) and the CLI never overrides it, so it isn't literally "conditioning on previous text" the way mlx_whisper's bug was. It can still hallucinate a plausible-sounding phrase and repeat it during a genuinely silent stretch, because nothing stops the decoder from being asked to transcribe silence in the first place. **Voice Activity Detection (VAD) is the actual fix** — it skips non-speech audio before it ever reaches the decoder. `whisperCppEngine.MainArgs` reads `config.WhisperVadModelPath` (a separately-downloaded ggml VAD model, e.g. `ggml-silero-v5.1.2.bin` from `https://huggingface.co/ggml-org/whisper-vad`) and appends `--vad -vm <path>` only when it's set — empty means whisper-cli runs exactly as before (opt-in, no behavior change for existing setups). Configured via the Settings panel's "whisper.cpp VAD model" field, which has no download/browse helper (a single file, unlike the model directory) — the user pastes an absolute path.

## Testing

`manager_test.go` and `runner_test.go` substitute a fake short-lived shell script for `mlx_whisper`/`ffmpeg`/`whisper-cli` (via the `resolveMlx`/`resolveFFmpeg`/`resolveWhisperCli` indirection on `Manager`, see `newTestManagerFull`) so the full state machine and subprocess-cancellation paths are exercised without needing a real install. Follow that pattern for new tests rather than requiring real binaries in CI. Note: `go test ./internal/... -race` currently fails on a pre-existing, engine-independent data race in `runner.go`'s `Cancel()`/`ForceKill()` (reads `cmd.Process` unsynchronized against `cmd.Start()`) — this project's own test command is plain `go test ./internal/...` (no `-race`), which passes cleanly.
